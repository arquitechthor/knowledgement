AWS IAM

Identity and Access Management · Ficha de Estudio SAA-C03
AWS Identity and Access Management (IAM) es el servicio centralizado de AWS para gestionar quién puede acceder a qué recursos y bajo qué condiciones. Permite crear y controlar identidades (usuarios, grupos, roles) y definir permisos granulares mediante políticas JSON. No tiene agente ni cliente instalable: opera exclusivamente a través de la API de AWS, la consola y la CLI. Clientes habituales: cualquier cuenta AWS — IAM es el punto de partida obligatorio para toda arquitectura segura. Aparece en el Dominio 1 (30%) del examen SAA-C03.

Casos de uso — Los SÍ y los NO
Cuándo sí usar IAM
  • Acceso programático a servicios AWS desde EC2/Lambda
  • Cross-account access con roles y STS AssumeRole
  • Least privilege en arquitecturas multi-servicio
  • Federación con IdP corporativo (SAML 2.0, OIDC)
  • Control granular sobre recursos AWS específicos
  • Service-to-service auth dentro de AWS
Cuándo no / Anti-patterns
  • Usuarios de apps móviles/web → usar Cognito
  • Hardcodear credenciales en código → usar roles
  • Credenciales de larga duración en EC2 → usar instance profiles
  • SSO entre múltiples cuentas → usar IAM Identity Center
  • AD/LDAP corporativo complejo → Directory Service
  • Usuario root para tareas diarias → nunca
Flashcard de Memoria Crítica
Trigger → Action · Memorizar para el examen
DENY EXPLÍCITO Si hay un Deny explícito en cualquier política, gana siempre. No importa cuántos Allow haya. Orden: Deny explícito > Allow > Deny implícito (default).
EC2 NECESITA ACCEDER A S3/DynamoDB Asignar IAM Role con Instance Profile. Nunca credenciales hardcodeadas ni access keys en la instancia.
ACCESO ENTRE CUENTAS AWS IAM Role en cuenta destino + STS AssumeRole desde cuenta origen. Nunca compartir credenciales entre cuentas.
RESTRINGIR ACCIONES EN CUENTAS HIJAS DE ORGANIZATION Service Control Policies (SCPs) en AWS Organizations. Las SCPs NO otorgan permisos, solo los limitan. No aplican a la cuenta master/management.
FEDERAR USUARIOS CORPORATIVOS (AD / SAML) IAM Identity Center (antes SSO) para múltiples cuentas. IAM directo con SAML 2.0 para una sola cuenta. Cognito para usuarios finales de aplicaciones.
AUDITAR QUIÉN HIZO QUÉ EN AWS AWS CloudTrail — registra todas las llamadas API de IAM. IAM Access Analyzer detecta acceso externo no intencionado a recursos.
PERMISSION BOUNDARY Límite máximo de permisos que un usuario/rol puede tener. No otorga permisos, define el techo. Útil para delegar creación de roles a developers sin escalada de privilegios.
POLÍTICA INLINE vs POLÍTICA GESTIONADA Inline: adjunta a una sola entidad, se borra con ella. Gestionada: reutilizable, versionable. Best practice: siempre política gestionada (customer managed > AWS managed para control).
TOKEN STS EXPIRADO / CREDENCIALES TEMPORALES Duración: 15 min – 12 horas para roles. No hay RPO/RTO — IAM es global y altamente disponible. Si expiran, la app debe volver a llamar AssumeRole.
USUARIO ROOT Solo para: cerrar la cuenta, cambiar el plan de soporte, gestionar billing root, recuperar acceso bloqueado. Proteger con MFA obligatorio. Nunca para operaciones del día a día.
Cuestionario Rápido — 5 Preguntas Tipo Examen SAA-C03
Validación de retención · IAM
PREGUNTA 01 / 05
Una empresa tiene una aplicación en EC2 que necesita leer objetos de S3 y escribir en DynamoDB. Un desarrollador propone crear un usuario IAM con access key y hardcodearla en el código. ¿Cuál es la solución correcta según los best practices de AWS?
A Crear un usuario IAM con acceso programático y rotar las credenciales cada 90 días
B Almacenar las credenciales en AWS Secrets Manager y recuperarlas desde el código
C Crear un IAM Role con los permisos necesarios y asignarlo a la instancia EC2 como Instance Profile
D Usar credenciales de root con MFA habilitado para mayor seguridad
Correcta: C. Los IAM Roles con Instance Profiles proveen credenciales temporales automáticamente rotadas por STS. No requieren gestión manual de secretos. Las opciones A y B siguen exponiendo credenciales de larga duración. La opción D viola el principio básico de nunca usar root para operaciones.
PREGUNTA 02 / 05
Una organización usa AWS Organizations con múltiples cuentas. El equipo de seguridad quiere asegurarse de que ninguna cuenta hija pueda crear recursos fuera de la región eu-west-1, incluso si un administrador de esa cuenta lo intenta. ¿Cuál es el mecanismo correcto?
A Crear una política IAM en cada cuenta que deniegue acciones fuera de eu-west-1
B Aplicar una Service Control Policy (SCP) en la OU que restrinja a eu-west-1
C Usar IAM Permission Boundaries en todos los usuarios de las cuentas hijas
D Configurar AWS Config rules para detectar y remediar recursos fuera de la región
Correcta: B. Las SCPs son el único mecanismo que restringe permisos a nivel de cuenta completa, incluyendo al administrador. Una SCP en la OU aplica a todos los usuarios y roles de todas las cuentas hijas. La opción A es eludible por el admin. La opción C requiere intervención en cada usuario. Config detecta pero no previene.
PREGUNTA 03 / 05
Un usuario IAM tiene una política adjunta que permite s3:GetObject en todos los buckets. Existe además una policy de bucket en S3 que explícitamente deniega s3:GetObject a ese usuario. ¿Cuál es el resultado cuando el usuario intenta leer un objeto?
A Acceso permitido porque la política IAM del usuario tiene prioridad sobre la bucket policy
B Acceso denegado porque el Deny explícito en la bucket policy prevalece sobre el Allow
C Acceso permitido porque las políticas IAM siempre superan las políticas de recursos
D Depende del orden en que se evaluaron las políticas
Correcta: B. El Deny explícito siempre gana, sin importar el origen de la política (IAM, bucket policy, SCP). La lógica de evaluación de AWS es: 1) Deny explícito → acceso denegado. 2) Allow → acceso permitido. 3) Ningún Allow → Deny implícito. No existe prioridad por tipo de política.
PREGUNTA 04 / 05
Una empresa quiere que sus empleados accedan a múltiples cuentas AWS usando sus credenciales corporativas de Active Directory, sin crear usuarios IAM individuales. ¿Qué solución es la más adecuada?
A Crear usuarios IAM en cada cuenta y configurar federación SAML con AD directamente
B Usar Amazon Cognito con User Pools conectado al AD corporativo
C Implementar AWS IAM Identity Center conectado al AD corporativo mediante AWS Directory Service
D Compartir una IAM Role entre todas las cuentas usando cross-account access con STS
Correcta: C. IAM Identity Center (antes AWS SSO) está diseñado exactamente para este escenario: acceso centralizado a múltiples cuentas con identidades federadas desde AD. Cognito (B) es para usuarios de aplicaciones, no para acceso a la consola AWS. La opción A funciona pero es compleja y no escala bien a múltiples cuentas.
PREGUNTA 05 / 05
Un equipo de desarrollo necesita poder crear roles IAM para sus aplicaciones, pero el equipo de seguridad quiere asegurarse de que esos roles nunca tengan más permisos que un conjunto definido. ¿Qué característica de IAM permite esto?
A SCPs aplicadas a la cuenta del equipo de desarrollo
B IAM Permission Boundaries definidas por el equipo de seguridad y requeridas en los roles
C Políticas IAM gestionadas por AWS (AWS Managed Policies)
D IAM Access Analyzer para detectar permisos excesivos automáticamente
Correcta: B. Los Permission Boundaries definen el máximo de permisos que una entidad puede tener, independientemente de las políticas que se le adjunten. Permiten delegar la creación de roles a developers sin riesgo de escalada de privilegios. Las SCPs (A) aplican a cuentas completas. Access Analyzer (D) detecta pero no previene.
